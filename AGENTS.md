# AGENTS.md

Файл памяти для ИИ-агента, который работает с этим репозиторием.
Прочитай его целиком перед первой правкой кода.

## 1. Что за проект

Сервис бронирования тайм-слотов по типу Calendly. Организатор заводит виды
активности и расписания, гость выбирает свободный слот и оставляет бронь.

Это эталонный проект курса «ИИ для разработчиков» (СФУ, Академия Softline).
Его читают студенты четвёртого курса направления «Web-программирование
и разработка ПО». Они уверенно владеют git, C#, ASP.NET Core, SQL, HTML, CSS,
JavaScript, React и Angular. Они впервые видят Docker, непрерывную интеграцию,
автоматические тесты, TypeSpec, агентов и MCP.

Отсюда главный критерий качества: код должен быть современным и честным,
но при этом читаться с первого раза на занятии. Не примитивным и не изощрённым.

## 2. Стек

| Слой                   | Технология                                                     |
| ---------------------- | -------------------------------------------------------------- |
| Язык                   | TypeScript в строгом режиме, Node.js 22 LTS                    |
| Веб-фреймворк          | Fastify 5                                                      |
| Проверка данных        | Zod 4                                                          |
| База данных            | SQLite через better-sqlite3 (синхронный драйвер)               |
| Контракт API           | TypeSpec, из него собирается OpenAPI 3.1                       |
| Интерфейс              | Vite, React 19, собственный CSS без библиотек компонентов      |
| Тесты                  | Vitest для модульных и интеграционных, Playwright для сквозных |
| Контейнер              | Docker, docker compose                                         |
| Непрерывная интеграция | GitHub Actions                                                 |

Репозиторий устроен как рабочие пространства npm (`workspaces`): один
`package-lock.json` в корне, четыре пакета внутри. Одна команда `npm install`
в корне ставит зависимости всех четырёх.

## 4. Как запускать

Установка зависимостей, из корня репозитория:

```bash
npm install
```

Наполнить базу демонстрационными данными:

```bash
npm run seed
```

Разработка: два окна терминала.

```bash
npm run dev:server
```

```bash
npm run dev:web
```

Интерфейс открывается на http://localhost:5173, запросы к `/api` уходят
на сервис через прокси Vite.

Собранный вариант, один порт:

```bash
npm run build
npm start
```

## 5. Как тестировать

```bash
npm run typecheck
npm test
npm run build
npm run e2e
```

`npm test` запускает 65 тестов Vitest: модульные на движок слотов,
интеграционные на все эндпоинты и тест соответствия контракту.
`npm run e2e` требует, чтобы проект был собран.

Пересборка контракта (нужна только при правке `main.tsp`):

```bash
npm run contract:build
```

## 6. Git-хуки перед коммитом

В папке `hooks/` лежат два git-хука. Они подключаются автоматически при
`npm install` (через `prepare`-скрипт), повторно настраивать вручную
не нужно. Если вдруг отключились — `npm run hooks:install`.

- `hooks/pre-commit` запускается перед каждым коммитом и проверяет:

  - в индексе нет `*.db`, `node_modules/`, `dist/`, отчётов Playwright
    и файлов `.env` (даже если их добавили через `git add -f`);
  - файлы `*.ts`, `*.tsx`, `*.tsp`, `*.md`, `*.json`, `*.css` прошли
    `prettier --check`;
  - обновлён `CHANGELOG.md` (генерируется из истории по Conventional Commits
    и автоматически добавляется в индекс);
  - `package.json` и `package-lock.json` синхронизированы;
  - если менялся `contract/main.tsp` — `contract/openapi.yaml` тоже
    пересобран компилятором TypeSpec;
  - `tsc --noEmit` проходит во всех воркспейсах, чьи файлы попали
    в индекс.

- `hooks/commit-msg` требует сообщение в формате
  [Conventional Commits](https://www.conventionalcommits.org/ru/):
  первое слово — тип (`feat`, `fix`, `docs`, `chore`, `refactor`, `test`,
  `build`, `ci`, `perf`, `style`, `revert`), затем опциональный
  `(scope)`, двоеточие, пробел и subject. Subject начинается со строчной
  буквы и не заканчивается точкой. Тип определяет, в какой раздел
  CHANGELOG попадает изменение.

Обойти хук (например, чтобы срочно закоммитить сломанный черновик) можно
через `git commit --no-verify`, но в обычной работе этого делать не нужно.

Если prettier предлагает переписать файл — запустите `npm run format`.
Если нужно прогнать все проверки, не делая коммит, — `npm run typecheck`
и `npm run format:check`.

Если хотите заранее увидеть, что попадёт в `CHANGELOG.md` (без коммита),
запустите `npm run changelog`. Скрипт перепишет файл и добавит его в
индекс — это удобно, чтобы посмотреть результат через `git diff --cached`
и при необходимости откатить через `git restore --staged CHANGELOG.md`.

## 7. CHANGELOG и Conventional Commits

`CHANGELOG.md` генерируется автоматически перед каждым коммитом из
истории git. Это требует, чтобы сообщения коммитов были в формате
[Conventional Commits](https://www.conventionalcommits.org/ru/).
Тип коммита определяет, в какой раздел CHANGELOG попадает запись:

| Тип коммита                                                   | Раздел CHANGELOG        |
| ------------------------------------------------------------- | ----------------------- |
| `feat`                                                        | Новое                   |
| `fix`                                                         | Исправления             |
| `docs`                                                        | Документация            |
| `perf`                                                        | Исправления             |
| `chore`, `refactor`, `test`, `build`, `ci`, `style`, `revert` | в CHANGELOG не попадает |

Примеры хороших сообщений для этого проекта:

```
feat: добавить эндпоинт отмены брони
fix(bookings): проверять активность при создании брони
docs: обновить README про запуск в Docker
chore: поднять версию better-sqlite3 до 12.4.1
```

Есть два варианта с scope, который сужает область:

```
feat(web): добавить страницу «Мои брони»
fix(api): правильно отдавать 404 при отсутствии активности
```

Технические подробности (как именно работает генерация) — в
`scripts/check-changelog.mjs` и `.changelog-config.cjs`.

## 8. Порядок работы Design First

Изменения вносятся строго в этом порядке:

1. Правим `contract/main.tsp`.
2. Пересобираем контракт: `npm run contract:build`.
3. Приводим схемы Zod в `server/src/schemas.ts` в соответствие с контрактом.
4. Правим обработчики в `server/src/routes/`.
5. Правим типы в `web/src/api.ts`.
6. Запускаем `npm test`.

Тест `server/tests/contract.test.ts` читает `contract/openapi.yaml` и требует,
чтобы приложение ему подчинялось: набор эндпоинтов, коды состояний и тела
ответов. Если начать с кода, этот тест упадёт. Так и задумано.

Коммитить `contract/openapi.yaml` обязательно: непрерывная интеграция
пересобирает контракт и сравнивает результат с тем, что лежит в репозитории.

## 9. Соглашения по коду

- Комментарии и тексты для пользователя на русском языке. Имена переменных,
  функций и файлов на английском.
- Комментарий объясняет решение, а не действие. «Здесь увеличиваем счётчик»
  не нужно. «Счётчик нужен, чтобы после брони перечитать сетку» нужно.
- Поля API в стиле `snake_case`: `duration_minutes`, `start_time`,
  `guest_email`. Так они названы в контракте, и менять их регистр по дороге
  значило бы держать в голове два словаря.
- Внутри кода имена в стиле `camelCase`: `buildSlots`, `weekdaysFromText`.
- Даты это строки «ГГГГ-ММ-ДД», время это строки «ЧЧ:ММ:СС». Объект `Date`
  используется только для вычислений и только в UTC: иначе результат зависел бы
  от часового пояса машины.
- Бизнес-логика вычисления слотов живёт в `server/src/slotEngine.ts`
  и не ходит в базу. Обработчик достаёт данные и передаёт их в чистые функции.
- Весь SQL лежит в `server/src/repository.ts`. В обработчиках маршрутов SQL нет.
- Проверка входных данных делается схемами Zod прямо в обработчике вызовом
  `schema.parse(...)`. Схемы Fastify на JSON Schema сознательно не используются:
  тогда описание данных существовало бы в трёх видах (TypeSpec, JSON Schema,
  типы TypeScript), а так их два, и типы выводятся из схем через `z.infer`.
  Ошибку `ZodError` превращает в ответ 422 общий обработчик в `app.ts`.
- Ошибки API это `ApiError` с кодом состояния, машиночитаемым кодом и текстом
  на русском. Тексты собраны в объекте `errors` в `server/src/errors.ts`,
  чтобы одна ситуация всегда описывалась одинаково.
- Строгий режим TypeScript включён вместе с `noUnusedLocals`,
  `noUnusedParameters` и `verbatimModuleSyntax`. Тип-импорты пишутся
  как `import type`.
- Функция помещается на экран. Если не помещается, её надо разделить.
- Русская типографика: длинных тире не используем, кавычки «ёлочки».

## 10. Чего делать нельзя

- Не добавлять зависимости без явной необходимости. Каждая новая строка
  в `package.json` это лишний шаг установки для студента на своём ноутбуке.
- Не подключать Tailwind, готовые наборы компонентов и библиотеки иконок.
  Интерфейс написан на собственном CSS намеренно: студенты должны видеть,
  как он устроен.
- Не менять SQLite на PostgreSQL. Причина в `docs/adr/0001-vybor-sqlite.md`.
- Не хранить слоты в базе. Причина в `docs/adr/0002-generatsiya-slotov-na-letu.md`.
- Не убирать частичный индекс `uq_active_booking` и не заменять оба рубежа
  защиты одним. Причина в `docs/adr/0003-zashchita-ot-dvoynogo-bronirovaniya.md`.
- Не править `contract/openapi.yaml` руками. Этот файл собирается компилятором
  из `contract/main.tsp`.
- Не ставить диапазоны версий (`^`, `~`) в `package.json`. Версии зафиксированы
  точно, чтобы через полгода собиралось то же самое.
- Не коммитить `booking.db`, `node_modules/`, `dist/` и отчёты Playwright.
- Не использовать длинные тире в русских текстах и комментариях.
- Не обходить хуки через `git commit --no-verify` без веской причины.
  Если хук упал — это сигнал, а не помеха.
- Не писать «умный» короткий код ценой понятности.

## 11. Частые задачи

**Добавить поле в модель.** Правим `contract/main.tsp`, пересобираем контракт,
правим схему Zod в `server/src/schemas.ts`, добавляем столбец в `SCHEMA`
в `server/src/db.ts`, правим запросы в `server/src/repository.ts`, удаляем
`booking.db` (миграций в проекте нет), правим тип в `web/src/api.ts`,
добавляем тест, запускаем `npm test`.

**Добавить эндпоинт.** Описываем операцию в `contract/main.tsp`, пересобираем
контракт, создаём или дополняем файл в `server/src/routes/`, подключаем его
в `server/src/app.ts`, добавляем тесты. Тест соответствия контракту сам
проверит, что список маршрутов совпадает со списком операций.

**Поменять правило генерации слотов.** Правим только `server/src/slotEngine.ts`
и `server/tests/slotEngine.test.ts`. Обработчики маршрутов трогать не нужно.

**Добавить новый код ошибки.** Добавляем значение в союз `ErrorCode`
в `contract/main.tsp`, пересобираем контракт, добавляем его в тип `ErrorCode`
в `server/src/errors.ts` и заготовку в объект `errors` рядом.
